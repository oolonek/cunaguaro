# Wikidata ontology and mapping: research notes

Sources read: [WikiProject Ontology](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology), its [Mapping subpage](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology/Mapping), and Centelles Velilla & Ferran-Ferrer, [*Using Wikidata’s Ontology in Practice*](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439) (2025, DOI: [10.5334/johd.439](https://doi.org/10.5334/johd.439)). The first two are community project/guidance pages, not a metabolomics ontology or a mandate to publish every database record to Wikidata; the Mapping page calls its upper-ontology mapping a **beginning**, subject to consensus, and says its “Specific cases” have **not yet been updated**. The project aims at improving the class tree and interoperability and points subject-specific work to projects such as [WikiProject Chemistry](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology#Interesting_Subpages).

## Mapping rules, from a Wikidata subject to an external ontology IRI

| Wikidata subject and relation to external target | Property | Qualification |
| --- | --- | --- |
| Class item ≡ external class | [equivalent class (P1709)](https://www.wikidata.org/wiki/Property:P1709) | Only a genuinely equivalent class; not a similar name or a subclass. |
| Wikidata property ≡ external property | [equivalent property (P1628)](https://www.wikidata.org/wiki/Property:P1628) | Property-to-property, genuinely equivalent. |
| Other item ≈ the **same external individual** | [exact match (P2888)](https://www.wikidata.org/wiki/Property:P2888) | Mapping-page category is individuals, **not** the default class-to-class mapping; P2888's property page describes a high-confidence interchangeable concept and has broader uses, so check the entity's type. |
| Wikidata class ⊃ external class (the external class is narrower) | [narrower external class (P3950)](https://www.wikidata.org/wiki/Property:P3950) | External class IRI as URL. No equivalent-class assertion. |
| Wikidata class ⊂ external class (the external class is broader) | **No currently designated direct external-class property in this guidance** | The page mentions [broader concept (P4900)](https://www.wikidata.org/wiki/Property:P4900) but immediately corrects itself: P4900 is **within Wikidata**. Its property page confirms it is an **Item-valued qualifier**, not an external URL link. Keep this relationship in the local crosswalk instead of misusing P4900/P1709. |
| Wikidata property ⊂ external property | [external superproperty (P2235)](https://www.wikidata.org/wiki/Property:P2235) | External target is the **broader** relation; WD father → external parent illustrates the direction. |
| Wikidata property ⊃ external property | [external subproperty (P2236)](https://www.wikidata.org/wiki/Property:P2236) | External target is the **narrower** relation. |

The mapping-page table/prose and worked examples are [here](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology/Mapping#Examples); some examples are explicitly labelled **“IS WRONG”** or **“CAUTION, SEEMS WRONG”**, not endorsed patterns. The page also asks for a consistent ontology IRI source/scheme, reserves a new dedicated external-ID property for *systematic* links to major ontologies (e.g. [BFO class ID P12602](https://www.wikidata.org/wiki/Property:P12602)), and illustrates classification of matched external ontology classes as instances of a metaclass plus [P279](https://www.wikidata.org/wiki/Property:P279)/[P1647](https://www.wikidata.org/wiki/Property:P1647) placement when Wikidata classes/properties actually exist. Its BFO/entity example warns that an apparently similar upper class may **not** be equivalent when ontological commitments differ ([Mapping: Comprehensive Mappings and Difficulties](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology/Mapping#Comprehensive_Mappings_to_Upper_Ontologies)).

A Wikidata class is itself an **item** (QID), not a property (PID); [P31](https://www.wikidata.org/wiki/Property:P31) means *instance of*, [P279](https://www.wikidata.org/wiki/Property:P279) means *subclass of* (all members of the subclass belong to its superclass), and a class can itself be an instance of a **metaclass**. Do not collapse class, compound individual, and relation, or infer that one observed feature is a subclass of a chemical. [WikiProject Ontology/Modelling](https://www.wikidata.org/wiki/Wikidata:WikiProject_Ontology/Modelling) explicitly distinguishes these levels, warns of real P31/P279 errors, and says Wikidata itself does not perform class inference. Properties are separately represented as Wikibase property entities ([Wikibase RDF format: Properties](https://www.mediawiki.org/wiki/Wikibase/Indexing/RDF_Dump_Format#Properties)).

## What the JOHD case actually does—and does not establish

[Sections 2–5](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439) present a **humanities** workflow about Francoist repression and book censorship: (1) inventory tables, rights, sensitive fields and stable local IDs/authority links; (2) align distinct persons/works/events/decisions to existing classes/properties, define item patterns and ShEx EntitySchemas, consult the community; (3) reconcile with **OpenRefine**, inspect existing claims, then make auditable referenced batches with **QuickStatements**; the abstract/conclusion also mentions **Mix’n’match** for matching. Use **WDQS/SPARQL** for coverage and missing-source audits. For complex decisions, the paper chooses a dedicated event item *or*, when context is modest, a sourced statement with qualifiers on the work; [WDQS direct `wdt:` values](https://www.mediawiki.org/wiki/Wikibase/Indexing/RDF_Dump_Format#Truthy_statements) alone do not retain the qualifiers and references available through statement nodes (`p:`/`ps:`/`pq:`/`prov:wasDerivedFrom`/`pr:`). The case's `wd:QH1` is illustrative notation, **not a valid asserted real QID**; the authors explicitly call the large local database a *testbed* “instead of uploading it to Wikidata” ([§§3–4](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439)).

[Wikidata EntitySchemas](https://www.wikidata.org/wiki/Wikidata:WikiProject_Schemas) are ShEx shapes against which selected items can be **tested**, whereas [property constraints](https://www.wikidata.org/wiki/Help:Property_constraints_portal) are editable-property **hints with possible exceptions**, not hard validation/uniqueness guarantees. The paper's Appendix A gives **short illustrative fragments**, not a turnkey chemical schema ([§2 and supplement](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439)). Its KG+RAG is **optional**, a prototype, and lacks full quantitative evaluation and curator-acceptance statistics; its pilot fragment/relation counts and claimed benefit cannot be extrapolated to metabolomics ([§§1, 6, 8](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439)).

**Licensing boundary:** Wikidata structured data, including EntitySchemas, is [CC0](https://www.wikidata.org/wiki/Wikidata:Licensing); the **paper itself** is [CC BY 4.0](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439). The authors require checking donor database rights/CC0 compatibility and avoiding indiscriminate bulk copying; individual uncopyrightable facts with explicit references are their cautious alternative when rights are uncertain ([§§3, 7–8](https://openhumanitiesdata.metajnl.com/articles/10.5334/johd.439)). Attribution to a source does **not** convert a restricted donor database into CC0-compatible bulk data ([Wikidata:Licensing](https://www.wikidata.org/wiki/Wikidata:Licensing)).

## Transfer to Peregrino metabolomics KG

Use Wikidata as an **alignment/reference layer**, not the required identity space for every RDB row: assign stable **local IRIs** to sample, acquisition/run, feature, spectrum, library hit/candidate and scoring/evidence records; attach an independently verified Wikidata QID only when the *same* eligible entity exists (e.g. an identified chemical, dataset or publication). [Wikidata notability](https://www.wikidata.org/wiki/Wikidata:Notability) requires a qualifying sitelink, a clearly identifiable entity describable by serious public references, **or** structural need; neither a local row nor a tentative annotation automatically passes. A feature-to-candidate mapping is **not** `P2888` identity and a candidate chemical is not proof of occurrence; retain original measured values, method, uncertainty, source, and candidate ranking locally. Before mapping chemical classes, check identity granularity (structure vs stereoisomer/salt/adduct vs measured ion) and subclass direction; do not promote approximate alignments to `P1709`/`P1628`. Reuse applicable chemistry properties and existing [identifier semantics](https://www.wikidata.org/wiki/Wikidata:WikiProject_Chemistry), draft a small local crosswalk with explicit *exact/narrower/broader/unmapped* status, and validate local record shapes separately; Wikidata shape/constraint claims are not an ingestion gate for this RDB. This is an **application of the cited method**, not a metabolomics model prescribed by either the WikiProject pages or the JOHD article.

## Multi-axial ontology is not a row-to-QID algorithm

[Doğan and Patel-Schneider, *A Multi-Axial Mindset for Ontology Design*](https://arxiv.org/html/2512.12260) argue that Wikidata's class hierarchy can support multiple, overlapping classification axes rather than one exhaustive upper-ontology tree (§§1–4). They distinguish structural classification from evidential disagreement (§3), acknowledge incomplete/inconsistent use (§5), and explicitly warn that materializing property-derived classes creates a statement explosion (§3). This is a conceptual preprint, not a metabolomics standard or a warrant to create one item/class per peak, feature, file, or scored match. Model mass, retention time, polarity, and spectral similarity as measured/scored **properties** of appropriately scoped local entities or activities, not as taxa or subclasses. Preserve the distinction between a taxon-class Wikidata item and a particular biological sample.

## Implementable graph boundary and tools

- **Source and identity:** Peregrino SQLite remains authoritative. Its `spectrum_files` and `processed_spectra` rows describe files, **not one spectrum per row**; `annotation_features` describes an accepted query feature within an annotation run; `annotation_hits` is a ranked candidate, not an identified metabolite (`peregrino/src/lib.rs`, `hocofaisan/src/main.rs`, `peregrino/ANNOTATIONS.md`). The registered Picoto audit TSV supplies the feature's retention time in **seconds** and selected raw-scan IDs; these are absent from the SQLite feature table (`picoto/README.md`, `peregrino/src/register.rs`). Processing settings/version are not stored with the Picoto registration, and the feature audit has no persisted hash; an export cannot honestly claim a fully reproducible processing activity from SQLite alone. Retain explicit unknowns, and capture the missing provenance at registration before publishing that assertion.
- **Local RDF:** First define a *versioned crosswalk* for biological entities, digital artifacts, computational activities, observations, and candidate evidence; each source field is assigned an RDF term, retained as raw source payload, or flagged as unmapped. Mint dataset-scoped local IRIs from durable identifiers and distinguish sample metadata rows from physical samples and raw scans from derived merged MS2 query spectra. Keep annotation-run versions, negative outcomes, and ambiguous matches. Use [PROV-O](https://www.w3.org/TR/prov-o/) for activities/artifacts and [PSI-MS controlled vocabulary](https://github.com/HUPO-PSI/psi-ms-CV) only where a precise term fits. A [USI](https://github.com/HUPO-PSI/usi) applies to an addressable deposited spectrum with real collection/run/index coordinates; it is not a generic feature ID or a constructed merged-MGF-spectrum ID.
- **Exporter:** For this existing Rust + SQLite project, a small read-only Rust projection can stream [N-Quads](https://www.w3.org/TR/n-quads/) using [Oxigraph's `oxrdfio`/`oxrdf` crates](https://github.com/oxigraph/oxigraph), with a source-snapshot/term-mapping manifest; an optional local [Oxigraph CLI](https://github.com/oxigraph/oxigraph/blob/main/cli/README.md) can load the export for SPARQL. [R2RML](https://www.w3.org/TR/r2rml/) is the standard declarative SQL-to-RDF mapping option, but this graph joins external audit files, computed run/lookup states and hashes as well as SQLite tables. [Ontop](https://ontop-vkg.org/guide/) offers virtual SPARQL over supported RDBMSs, but its [listed supported systems do not include SQLite](https://ontop-vkg.org/guide/) and its [generic JDBC path explicitly says not to rely on it](https://ontop-vkg.org/guide/databases/generic.html); do not prescribe it here without a validated connector or source migration.
- **Validation and publication:** [SHACL](https://www.w3.org/TR/shacl/) shapes using [Rudof's Rust validator](https://rudof-project.github.io/rudof/) via `peregrino kg validate` check the **local RDF** for cardinalities, link targets, units, and score datatypes; compare source/export counts and failed/zero-hit/candidate histories separately. [Wikidata ShEx EntitySchemas](https://www.wikidata.org/wiki/Wikidata:WikiProject_Schemas) and property constraints describe **curated Wikidata items** instead. Use Cunaguaro's exact identifier reconciliation plus manual review for ambiguous results. Only later consider referenced, rights-compatible Wikidata contributions for independently eligible entities; [Wikibase Suite/Cloud](https://www.wikidata.org/wiki/Wikidata:Notability#Alternatives) is an optional *separate* instance if local editable Q/P-style records are essential, not a prerequisite for RDF or a way to turn local QIDs into Wikidata QIDs.
